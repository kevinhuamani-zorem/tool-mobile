📁PASO 1: Revisar la estructura de los Test

                Archivos .feature. ==> Capa de Cucumber
                ├── Archivos de definiciones de pasos (.ts)
                │    └── screenObjects
                │    └── Utils
                ├── Archivos Json de datos (Locators)
                │    └── Archivos de usuarios .yml
                └── Artefactos a probar
                     └── .ipa, .app, .apk
Plantear el Escenario de Pruebas
- Debe estar escrito en lenguaje Gherkin (Given, When, Then)
* Solo este lenguaje debe ser escrito en español

Ejemplo:

Scenario Outline: Validar dirección de usuario
Given el usuario Carlos Barboza TFT inicia sesión en Yape
When el usuario selecciona la opcion tienda
Then validar dirección
| Jirón Lima | Barranco | 2 |

📁PASO 2: Crear/Editar un archivo feature

            fwk-mobile-test/
                ├── features/                        # Test cases folder.
                │   ├── yape-features/               # Test scenarios written in Cucumber.
                │   │   └── marketplace/             # Test scenarios related to Marketplace.
Editar un archivo .feature existente
- Revisar los features existentes si se ajusta y se puede incluir el nuevo escenario en alguno de ellos.
Ejemplo: Si el nuevo caso de pruebas esta relacionado a dirección, se puede incluir este nuevo caso en el archivo:
address.feature
Crear un archivo .feature
- Nuevas funcionalidades que no están cubiertas por los features existentes deben tener su propio archivo .feature.
Ejemplo: Si el nuevo caso de pruebas esta relacionado a la funcionalidad de "Ofertas", se debe crear un nuevo archivo:
offers.feature
Escribir el caso de pruebas en formato Gherkin (Given, When, Then)
- Se debe considerar el uso de tags para identificar las escenarios que se ejecutarán de acuerdo a la configuracion de los archivos wdio
Ejemplo: @marketplace, @smokeTestMarketplace

📁PASO 3: Determinar los locators

             fwk-mobile-test/
            │   │   └── locators/                # JSON locators to identify UI elements for testing
            │   │         └── marketplace/       # JSON locators related to marketplace test.
Incluir los locators en el archivo .json
- Obtener los locators necesarios para el nuevo caso de prueba y agregarlos al archivo .json correspondiente.
- Si es una nueva funcionalidad se debe crear un nuevo archivo .json.
- En el archivo .json se deben seguir las convenciones de nombrado y estructura.

- Los locators se deben obtener para ambas app (iOS y Android).

Ejemplo:

"MarketPlaceAddressAndroid": { "txtChangeAddress":"//android.widget.Button[@text=\"change address\"]", }

"MarketPlaceAddressIos":{ "txtChangeAddress":"//XCUIElementTypeButton[@name=\"change address\"]", }

📁PASO 5: Crear/Editar un archivo step definition

            fwk-mobile-test/
            │   ├── yape-step-definitions/       # Step Definitions code links Gherkin specifications.
            │   │   └── marketplace/             # Step Definitions related to Marketplace.
Crear/Editar la linea de definición funcional
- Se incluye la implementación de la lógica de prueba
- Se puede llamar a los métodos creados en el paso anterior.

Ejemplo:
- En este caso es la implementación de la lógica de prueba para un paso de Gherkin que usa la palabra clave "Then"

Then('validar dirección', async (address: DataTable) => {
await addressScreen.txtChangeAddress.waitForDisplayed({ timeout });
if (await addressScreen.txtChangeAddress.isDisplayed()) {
const [direccion, distrito, etapa] = address.raw()[0];
await addressScreen.validateAddress(direccion, distrito, etapa);
}
});

🐛Tips de Debugging

Comando/Técnica Uso para MOBILE
Log de códigos de prueba: print, console.log('MENSAJE'), console.error('Error during address validation flow:', error) Logs enviados a consola
Logs del servidor de Automatización (Appium) Muestra los comandos Json exactos que se envian al dispositivo
Herramientas de Inspeccion de Elementos (Appium Inspector) El 90% de fallos se produce a que el selector de los elementos es inestable
Manejo de Esperas y Tiempos Fallos intermitentes por problemas de sincronización de ambientes, por lo que es importante implementar esperas explícitas
Asegurarse que el fallo no se deba al entorno de prueba Con la aplicación en estado limpio, desinstalada con la cache borrada antes de cada escenario
